# Implementation Decisions and Open Items

**Last updated:** 2026-11-13
This file records user-approved direction and unresolved design choices. It must not be interpreted as proof that planned changes are implemented. The current source map and implementation facts are in [PROJECT-STATUS.md](PROJECT-STATUS.md).

## Approved direction

1. **Cost discipline:** Do not add a paid Azure service or increase VM/disk footprint without explaining incremental cost and getting approval. Prefer existing CM/workload compute and OS disks where safe. Existing remote Terraform state, Key Vault, and compute have baseline costs; “no extra cost” means avoid unnecessary new/expanded resources, not that Azure usage is free.
2. **HA shape:** Keep multiple CM nodes across zones, initially 2–3 and a design ceiling of 5 subject to quota/cost checks; preserve workload HA and do not add a VM or Azure Load Balancer solely for telemetry. Loki uses shared Blob with replication factor 1; Alloy pushes metrics to each CM Prometheus, while each log stream is sent once through a local proxy that fails over across Loki nodes.
3. **Prometheus and Alloy:** Alloy is the sole system metrics/log agent, embedding the unix exporter. Allowlist essential metric series, scrape every 15 seconds, and remote-write concurrently to all CM Prometheus endpoints using Tailscale DNS TLS and WAL. Prometheus runs on each CM as a TLS push receiver, keeps local TSDB, and only self-scrapes. Remove the per-replica label from alert notifications so Alertmanager's HA pair can deduplicate duplicate evaluations. PostgreSQL metrics remain basic service/readiness scope.
4. **Loki:** Use shared Azure Blob as the stateless/shared chunks+TSDB object store; each CM runs Loki with memberlist over Tailscale and `replication_factor: 1`. Alloy emits each log once to loopback Nginx; the proxy round-robins/fails over over verified TLS to CM Loki peers. Use 30m idle and 1h max chunk age to batch Blob transactions, retain 7 days, and keep local WAL/index/cache only as working state. Do not use a paid Azure Load Balancer. This replaces the earlier local-filesystem Loki and Alloy log-dual-write proposal.
5. **Key Vault network:** Keep Key Vault for workload managed-identity runtime access to Cloudflare secret. Target a Key Vault service endpoint and firewall allowlist for only workload subnet(s), default deny; avoid the Private Endpoint/Private DNS cost if the service-endpoint design fits. This requires Key Vault public network access through its firewall (not unrestricted public access) and coordination of subnet IDs across Terraform roots. The design is not implemented yet.
6. **Encryption:** HSM is not required. Storage uses Azure-managed encryption by default. Customer-managed Storage encryption is opt-in via Terraform `enable_storage_cmk` (default `false`) and GitHub repository variable `ENABLE_STORAGE_CMK=true`; set `STORAGE_ENCRYPTION_KEY_NAME` consistently for both Terraform roots if using a custom key. When enabling it, apply the identity root first so the Key Vault key exists before planning/applying the VM-resource root. This may incur Key Vault key-operation charges and adds key lifecycle/availability responsibilities. Do not select Premium/HSM-backed keys without explicit cost/compliance approval. Preserve Key Vault RBAC, workload identity, TLS, and secret handling in the default configuration. Existing deployments that already use CMK should set the variable to `true` before planning; switching it off changes the Storage Account encryption association and requires deliberate plan/recovery review.
7. **Automation context:** Agents must start from `PROJECT-STATUS.md`, inspect only source files relevant to the requested task, avoid retired `.github/agents/` and `docs/` context unless explicitly asked, and update the status/decision record in the same change when implementation or architecture decisions change.
8. **Ansible security gate:** Run Checkov's Ansible framework in the Ansible pull-request workflow as a hard-fail merge check. Use the existing Tailscale-issued certificates (no additional paid service) to protect monitoring APIs exposed on the tailnet. Keep narrowly scoped Checkov inline exceptions only for HTTP health endpoints that are loopback-only; document the binding/firewall reason beside each exception. Do not globally skip HTTPS policies.

## Open decisions and validation before rollout

### Ansible Checkov scan

Checkov 3.4.4 scanned the `ansible/` directory with `--framework ansible`: 55 checks passed, 0 failed, and 13 skipped. The failures were all Checkov's blanket HTTP-URI policy. Exposed Prometheus, Alertmanager, and Grafana health paths are HTTPS with system certificate validation; Alertmanager TLS reuses the existing Tailscale certificate. Remaining exceptions are task-local health probes to loopback services, with task-level explanations; the workload proxy binds loopback by default and the optional Azure Load Balancer probe listener is separately source-restricted. The CI Checkov action is configured as a hard gate. No paid security add-on was needed for these fixes.

GitHub workflow YAML alone cannot enforce repository merge rules. Configure `Ansible Check HA / Ansible Check and Security` as a required status check in the `main` branch protection/ruleset; otherwise the workflow reports failures but an authorized user may still bypass the check and merge.

Customer-managed Storage encryption is a separate cost choice, not a Checkov remediation: Azure-managed encryption is now the default. Opt-in CMK can incur Key Vault key-operation charges and adds key lifecycle responsibilities; see approved decision 6 and the Terraform variable `enable_storage_cmk`.

### Shared dispatcher coordination and Blob retention

The Storage Account has two distinct consumers: Loki object storage and the recovery dispatcher's shared cooldown/lease state. The approved current direction keeps both uses; Loki is stateless with respect to long-term chunk/index storage, while dispatcher state remains shared for action deduplication. Any future removal of the Storage Account must separately replace or retire dispatcher coordination; a local file lock is not shared HA state. Do not delete the `recovery-state` container or its RBAC/resource dependencies as part of this Loki change.

The Terraform remote state backend is separate and should not be changed as part of this decision.

### PostgreSQL HA for the three-workload lab (architecture selected; source implemented, runtime acceptance pending)

The currently provisioned control-manager pool remains **two CMs**. Five CMs is future scale-out only and requires a separate quota/headroom decision; it is not part of the current deployment target. The requested target workload pool is three VMs across zones, with each VM running the web/app tier and participating in one PostgreSQL HA cluster. Do not model this as three independent local databases.

Recommended self-managed stack, avoiding a separate database VM and paid Azure Database for PostgreSQL:

- PostgreSQL native streaming replication managed by **Patroni** on all three workload VMs.
- A three-member **etcd** DCS on those same VMs for quorum and leader state. Loss of one VM leaves two DCS voters; this co-location is the low-cost lab choice and creates CPU/RAM contention, so size/load-test it. A more isolated production deployment may place DCS or database resources on separate fault domains, increasing cost.
- **HAProxy** on each workload VM, with health checks against Patroni's primary endpoint, gives the local app a stable loopback write endpoint (separate port from PostgreSQL). Apps must reconnect/retry safely after failover.
- PostgreSQL data storage gets an explicit per-workload optional managed data disk. Default remains no data disk (database files on the OS disk) to keep the lab cost down; enabling the option attaches/formats/mounts a disk and points PostgreSQL data there, with the added disk cost accepted for deployments that need OS/data separation. A data disk is not a backup or a replication mechanism. Validate PostgreSQL ownership, permissions, mount ordering, upgrade/migration, and recovery before rollout.
- Prefer synchronous replication with one synchronous standby for purchase/inventory-style writes. This trades write availability/latency for a lower acknowledged-data-loss risk: writes may block when a synchronous standby is unavailable. **Agreed targets (not guarantees):** on a single DB-member loss, RPO is zero loss of acknowledged transactions while a synchronous standby is healthy and selected; failover RTO is 300 seconds. For disaster recovery from base backup plus WAL, PITR RPO is 300 seconds (maximum archive lag target) and restore RTO is 7,200 seconds. These goals require fault/restore tests and measured application behavior before they can be called achieved. Loss of quorum, absent synchronous standby, a correlated zone/account failure, or a stale/incomplete backup can violate availability or recovery objectives. Patroni's synchronous mode does not replace backup or fencing.
- Require a split-brain/fencing design (Patroni watchdog if the Azure VM exposes a reliable watchdog, plus DCS quorum and demotion behavior), TLS/authentication on replication and DCS APIs, private-only firewall rules, and tested failover/rejoin. Do not declare HA complete until partition/failover tests show only one writable primary.
- **Approved backup destination:** use a dedicated private `postgres-backups` container in the existing Blob Storage Account, separate from Loki's container and Terraform state; do not create another Storage Account for this lab. Give a dedicated backup workload identity only container-scoped data-plane permissions and attach it only to DB members. Keep a separate lifecycle/retention rule for this container; do not let Loki's lifecycle policy expire database backup objects. The 7-day PITR target uses 9-day Blob deletion lifecycle as a two-day cushion; it is not immutable retention or an independent backup boundary. The account remains a shared failure/security boundary, so stronger isolation (separate account/subscription, immutable vault or independently administered copy) remains a future production option with additional cost.
- Local backup copies on OS disks are possible as an extra recovery copy, but are tied to the VM/OS-disk lifecycle and share host, administrative and often zone failure domains. Putting the backup on the optional DB data disk is not independent protection: loss/corruption of that disk can take out both database files and backup. Keeping copies on all three nodes may preserve a copy after one VM loss, but does not protect against a bad backup, operator deletion, ransomware/credential compromise, cluster-wide corruption, or loss of the remaining nodes. Treat local copies as cache/short-term convenience, not the only backup.
- Implemented backup policy: **daily base backup plus continuous WAL archiving**, with a 7-day PITR target and 9-day Blob lifecycle deletion. WAL archive timeout is 5 minutes. The helper uploads SHA-256 manifests and uses conditional create-only writes for base/WAL objects; this is not Azure immutable storage protection, and the backup identity can still overwrite/delete within its granted contributor scope. Last-success metadata is intentionally mutable. Static helper tests do not establish Azure authorization, Blob networking, archive continuity, or point-in-time restorability. Require a production-like restore drill that verifies WAL continuity and measured recovery time before calling the database recoverable. Seven days remains a lab choice, not a universal production standard; business, legal, compliance, storage-growth, and cost requirements can require more.
- The current sample Python app is a static HTTP responder, not a database client. Add a small transactional demo (idempotency key and atomic inventory update) before claiming the full request path is represented. Never use cached/Redis inventory as the source of truth for stock decrement; Redis is optional read-cache work only.

Capacity warning: Standard_D2ps_v6 is 2 vCPU per VM. Two CM + three workload VMs consume 5 VMs / 10 vCPU, which exactly uses the reported subscription ceiling and leaves no headroom. Scaling to five CMs while retaining three workload nodes would need 8 VMs / 16 vCPU, plus the required regional/family quota and actual SKU availability. Treat five CMs as a future quota increase, not a current deployable topology. Co-locating PostgreSQL/etcd/app on 2-vCPU workload VMs is a demonstrator configuration until representative load tests establish safe capacity; it is not automatically production-ready for arbitrary customer workloads.

Very rough Central India retail estimate (730 hours/month, USD, before taxes/discounts): the third 2-vCPU workload VM is about **$34/month compute**, and its 64-GiB Standard SSD LRS OS disk about **$5/month**. Thus 2→3 workload VMs adds roughly **$39/month**. If all three PostgreSQL members get optional 64-GiB data disks, add about **$16/month**; 128-GiB data disks add about **$32/month**. A small 100–300 GiB Hot LRS backup footprint is roughly **$2–$6/month** for capacity, plus operations/retention. A reasonable rough delta for 3 workloads with 64-GiB data disks on all three and modest backups is **about $57–$65/month**, relative to the existing two-workload topology. Default OS-disk-only DB data would be closer to **$39–$45/month**. These estimates omit significant backup growth, blob transactions, network egress, and any quota/VM size changes; current subscription quota exactly fits 2 CM + 3 workload VMs, with no safety headroom.

Availability objective: **99.9% is a target, not a guarantee**. It permits about 43.8 minutes of unavailability per 30-day month. PostgreSQL failover can still break in-flight connections; app retries/idempotency, multi-zone placement, quorum/fencing, health-based routing, backup restore, and monitoring are necessary to approach the target. Synchronous replication reduces the chance of losing acknowledged writes but may reject/block writes when the synchronous standby is unavailable. The application owner must choose acceptable RPO/RTO and whether write availability or acknowledged-write durability wins during degraded operation. An architecture cannot promise both zero interruption and zero data loss under every partition/failure.

**Deployment rollback is not database restore.** A failed Ansible/app rollout should normally roll back application/configuration while keeping the live database and all transactions written during rollout. It must not automatically restore the pre-rollout DB backup: that would erase legitimate purchases/inventory changes made since the backup. Schema changes must use backward-compatible expand/migrate/contract steps so old and new app versions can use the schema during the rollout. A database PITR restore is a separate disaster-recovery action for corruption/data damage, with an explicit recovery point, write freeze/cutover, data-loss approval, and operator decision; it is not the routine rollback for a failed code deployment.

The agreed topology and main configuration are now **implemented in source**, including explicit three-member inventory, optional data disks, Patroni/etcd/HAProxy, transactional demo app, Blob backup helpers, and monitoring. Terraform validation, Ansible lint/syntax checks, and nine local Python unit tests pass. The full repository validation script reaches its final `git diff --check` but fails on whitespace reported across broader existing workspace changes; this is not treated as a clean full-suite pass. No Terraform plan/apply, Ansible deployment, Azure Blob integration test, failover/partition test, database restore drill, capacity test, or Azure VM watchdog test has been performed. The configured `softdog` watchdog must be proven to provide the required fencing behavior before relying on it; PostgreSQL/etcd TLS certificate renewal currently avoids independently restarting HA services and needs an operator-coordinated rotation procedure. Current quota estimate is exactly 5 VMs/10 vCPU for 2 CMs + 3 workloads, with no headroom. **Terraform apply/deployment remains separately authorization-gated.**

### Alloy fan-out, Loki proxy and alert deduplication

Alloy 1.5 metrics WAL is configured with finite retention (24h maximum); its effective backlog and behavior when one or more CM receivers are unavailable still need runtime checks. Loki log WAL is enabled but experimental in the pinned Alloy and requires the service's experimental stability flag; test restart, backpressure and disk use. Nginx uses passive failure detection and no Azure Load Balancer; verify actual failover timings and that HTTPS SNI/certificate verification works for every dynamically discovered tailnet FQDN. Alert relabeling drops only `replica`; test that a single incident results in one notification/recovery action.

Loki uses Blob for shared long-term data and local disk for WAL/index cache. Verify its memberlist ring across 2–5 CMs, read/write availability after a CM loss, shared Blob connectivity, compactor behavior, and cleanup lifecycle. Set Loki chunk idle/max age to reduce small object writes while recognizing this may delay object-store visibility of unflushed chunks; query behavior should be checked across peers. No Azure resource or disk is added by this observability design.

### Grafana Loki datasource and local TLS

Grafana currently reaches Loki through the local Nginx proxy on port 3101, whose upstream connections use verified HTTPS to CM Tailscale DNS names. The requested direct `http://localhost:3100` datasource is not yet configured: Loki currently listens on the CM's Tailscale address with TLS, so changing only the datasource URL would fail or weaken the intended TLS boundary. If direct loopback HTTP is still required, first design a loopback-only listener/proxy path that preserves HTTPS for all tailnet traffic and cannot expose plaintext on the tailnet or VNet; then update and validate the Grafana datasource accordingly.

Prometheus source currently drops only the `replica` label from outgoing alerts. Runtime acceptance still requires confirming Alertmanager HA grouping and that a single logical incident does not trigger duplicate notifications or remediation actions.

### Approved-release canary rollout and rollback (code present; acceptance pending)

The rollout implementation now packages the triggering reviewed SHA (or an operator-selected full SHA via protected manual dispatch) in GitHub Actions, stages the checksum-verified release on every ready CM over Tailscale SSH, runs a single-workload canary then percentage-based workload batches from one controller, applies CPU/memory/disk and service gates, and attempts rollback to the last fully successful release. CI synchronizes the last-good pointer across the ready CM set only after deployment succeeds. CM cloud-init no longer clones the public GitHub URL; nodes do not require repository access or a GitHub credential. Controller output is appended to `/var/log/ansible/site.log` for Alloy collection. Treat this as code present only: deployment behavior, alarms, rollback, private-repository operation and controller failure recovery have not been accepted by tests.

Implement a release-based flow so either a public or private source repository can be used without giving CM/workload nodes a long-lived GitHub credential:

1. Keep protected GitHub Environment approval before archive transfer. The CM archive is verified by SHA-256 and embedded commit marker; audit this trust boundary and preserve immutable SHA directories.
2. The current canary is one non-database workload; workload concurrency defaults to `25%`, control nodes are serialized, and the canary observation pause is configurable. Validate percentage rounding, inventory limits, and recovery at 1, 2, and larger host counts.
3. Current gates include workload HTTP/app health, root disk usage, available memory, and CPU load. Add or validate Prometheus alert-state checks and post-batch observation before claiming full rollout health.
4. On a stage failure the script stops and re-applies the last successful source to the changed scope. First deployment cannot auto-rollback. Database/data migrations and irreversible changes remain outside automatic rollback unless backward compatible.
5. A deployment-failure metric and Prometheus alert exist, and logs go to Alloy. There is no external human-notification receiver configured; approve a channel and credentials separately. Ensure failure and rollback-failure states remain visible after a CM/controller loss.
6. Test success, canary failure, mid-batch failure, health-gate failure, controller interruption, checksum/path rejection, first-deploy failure, rollback failure, private repository checkout at CI, and rollback selection. No runtime test has yet run.

No deployment automation should run Terraform apply or expand infrastructure as part of this feature. This is a moderate workflow/Ansible change, not just changing the Git URL; current `run.sh`/site execution, cloud-init repository bootstrap, health checks, and protected environment workflow need coordinated updates.

### Cloudflare Tunnel ingress-gateway scaling and routing (code present; acceptance pending)

Current code configures a single tunnel ID and selects only explicitly Terraform-tagged `cloudflare_ingress=true` VMs into a generated inventory group. The default has two ingress nodes; all workload nodes remain app backends. A 15-second watchdog withdraws an ingress connector after repeated proxy-to-any-backend readiness failure and re-enables it after repeated successful checks. Nginx selects all online workload backends with `least_conn` and bounded passive retry. This avoids needing 10 tunnels solely because there may be 250 application VM backends: connector count remains the tagged ingress subset, below the configured cap. No Cloudflare Load Balancer product is configured. This is not yet runtime-validated and does not guarantee request-level zero loss or CPU/RAM-aware routing.

Cloudflare's official [Tunnel availability and failover guidance](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-availability/) distinguishes replicas from traffic-steering pools: replicas of one tunnel provide availability, Cloudflare routes to a geographically closest replica without round-robin/health-aware steering, and Cloudflare recommends Cloudflare Load Balancing when intelligent distribution across multiple tunnel origins is required. Cloudflare's [published applications guidance](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/) supports routing via DNS CNAME or a public Load Balancer to tunnel UUID hostnames. Reconfirm current plan limits/pricing and account behavior before implementation.

The no-Load-Balancer design uses one public hostname and one Tunnel with a small number of connector gateways (default 2; scale the tagged gateway set only when capacity testing justifies it), while Nginx on every VM can proxy to the app pool. This removes the prior plan to put all 250 VMs in one Tunnel or to create 10 tunnels at connector 25/26 boundaries. Cloudflare replica selection is not promised to be even or resource-aware; ensure each ingress node can forward to healthy peers. Multiple public tunnel origins or per-tunnel automatic traffic steering would require a separately approved Cloudflare Load Balancing or other supported routing design. Confirm actual account cap and connector behavior before rollout.

Implementation requirements/open decisions:

- Source of truth is the Terraform `cloudflare_ingress` VM field/tag, copied into Azure VM tags and discovered by managed-identity inventory generation. This is stable across adding ordinary app nodes; intentionally changing gateway tags changes connector membership. Validate this with Terraform plans and inventory tests.
- Decide if tunnel creation, token issuance, published-app route, and Load Balancer pools are Terraform/provider/API-managed or controlled out-of-band. Use least-privilege scoped Cloudflare API credentials, stored in Key Vault and accessed only at runtime/approved automation; never put tokens in Terraform state, inventory, logs, or committed vars. Existing runtime token logic only fetches a token for a preconfigured tunnel ID.
- Define Cloudflare health checks/failover and origin mapping for the public hostname. Ensure WAF is still applied before requests reach any tunnel origin and validate TLS/Host preservation.
- Each connector's local Nginx proxies to the complete workload group, and `/readyz` checks that at least one app backend responds. `least_conn` is request-count based, not resource-aware. The watchdog may withdraw a gateway after consecutive readiness failures; verify Cloudflare response/retry timing and avoid flapping. Do not claim CPU/RAM-aware balancing without a separate implementation and tests.
- Test adding/removing nodes around 25/26, 50/51 and 249/250; verify stable pool assignment, tunnel health, public traffic distribution, WAF, failover when a tunnel/pool is unhealthy, and costs. Preserve the existing manual configuration as the safe behavior until routing and automation are approved and tested.

#### Preferred no-Cloudflare-Load-Balancing candidate

To avoid Cloudflare Load Balancing charges, prefer **one public hostname and one Cloudflare Tunnel with a small set of ingress connectors (for example 2–5 existing workload VMs, always below the verified connector limit)**, rather than one connector/tunnel per application VM. Each ingress connector's local Nginx should proxy across the full application workload pool, using TLS and passive backend failure handling. The remaining workload VMs can run the app/Nginx backend without a Cloudflare connector. This keeps Cloudflare's tunnel replicas as ingress availability only; Cloudflare does not promise even or resource-aware selection among replicas, so every selected ingress node must be able to serve as an equivalent gateway and forward to healthy peers.

Add a local readiness/watchdog for each ingress node: if its Nginx proxy/data path is unhealthy for a configured consecutive-failure window, stop that node's `cloudflared` connector so Cloudflare can use another still-connected replica; only re-enable it after readiness recovers and a cooldown passes. The check must distinguish proxy readiness (able to reach at least one healthy app backend) from the ingress VM's own app health, because a gateway whose local app failed can still be a healthy gateway if peer backends work. Keep bounded retry/timeout behavior and emit an alert when recovery does not succeed. Validate whether Cloudflare shifts requests when a connector is stopped and test existing/in-flight requests; do not promise zero failed requests during the health-detection interval.

The current Nginx `least_conn` and passive `max_fails` behavior is a starting point, not CPU/RAM-aware scheduling or active health checking. Backend health checks and excluded-node behavior need explicit implementation and failure tests. A single PostgreSQL primary remains a shared failure domain; Nginx/tunnel failover cannot make database-dependent writes succeed while that database is unavailable. This candidate needs no extra VM or Cloudflare Load Balancing product, but incurs engineering/monitoring work and is not implemented or runtime-accepted. Confirm the account-specific connector cap and current Cloudflare behavior before coding.
