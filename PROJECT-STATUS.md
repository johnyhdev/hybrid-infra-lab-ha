# Project Status and Source Map

**Last updated:** 2026-11-12  
**Purpose:** canonical, concise starting point for coding agents and maintainers. This describes what the checked-in code does now and what is only an agreed target. It is not evidence that cloud deployment or HA acceptance tests have passed.

## Goal and constraints

Build a small, cost-conscious, multi-zone Azure lab with private CM and workload pools. Current topology remains two CMs; five CMs is future scale-out only, subject to additional quota and headroom. The requested HA lab target is three workload VMs (the current checked-in default still has two), subject to the reported 5-VM/10-vCPU subscription limit and runtime capacity testing. Keep management and service access identity-based and least-privilege (GitHub OIDC, managed identities, Tailscale); avoid public VM IPs and unnecessary paid services. Do not claim zero cost: existing Azure compute, disks, Key Vault, remote Terraform state, networking, and retained storage have their normal charges. Add paid services only after explicit cost/benefit approval.

## Current implementation (code facts)

### Terraform and Azure

- `terraform/01-identity/` provisions the persistent resource group, CM and workload user-assigned identities, RBAC, and a Standard Key Vault. Key Vault currently has public network access disabled, default-deny network ACLs, soft delete and purge protection. It also creates an RSA-4096 key named for Loki CMK.
- `terraform/02-vmresource/` provisions the VNet/subnets, NSGs/rules, private-only VM NICs and Linux VMs, cloud-init inputs, optional load-balancer scaffolding, and a ZRS Storage Account currently used by Loki **and** dispatcher state. The storage account has public access and Shared Key disabled, CMK configured, and separate `loki` / `recovery-state` containers.
- Defaults define two `Standard_D2ps_v6` ARM64 CM VMs and two workload VMs across zones, each with a 64-GB OS disk and no separate data disk. The subscription estimate of 5 VMs/10 vCPU fits 2 CM + 3 workload VMs at this SKU with no headroom; scaling CM to 5 while keeping 3 workloads would require 8 VMs/16 vCPU and a quota increase. Workload map capacity is a provisioning limit, not autoscaling.
- `terraform/02-vmresource/network.tf` currently creates Private DNS zones and Private Endpoints for Blob and Key Vault. These are current code, not the desired lower-cost Key Vault networking target below.
- Terraform state is a separate concern: each root has an Azure Blob backend in its own `backend.tf`. Do not confuse that pre-existing remote state backend with the Loki/recovery Storage Account.
- **Terraform still reads a Key Vault key:** `terraform/02-vmresource/main.tf` declares `data.azurerm_key_vault_key.loki_encryption_key` and configures the Storage Account CMK. Therefore Terraform plan/apply currently needs the relevant Key Vault data-plane access. This lookup is unrelated to Cloudflare Tunnel runtime retrieval.

### Ansible and runtime services

- `ansible/playbooks/site.yml` imports baseline, application, and monitoring playbooks. Baseline/application apply common OS, disk, Tailscale TLS, Loki proxy, and Alloy roles; the standalone Node Exporter role is no longer invoked. `application.yml` configures workload app/Nginx/Cloudflare Tunnel/log collector/resilience and PostgreSQL on the single designated database VM. The sample app currently does not connect to PostgreSQL. `monitoring.yml` runs recovery dispatcher and monitoring stack on control nodes.
- Role source of truth is `ansible/roles/*/tasks/`, with rendered configs under each role's `templates/`, host/group settings under `ansible/group_vars/`, and inventory under `ansible/inventory/`.
- Prometheus runs on each CM as a push receiver and self-scrapes only. Alloy's embedded `prometheus.exporter.unix` replaces the standalone Node Exporter service: it collects selected system metrics on CM/workload nodes, filters series in Alloy, and pushes to every control Prometheus over Tailscale FQDN TLS. Retention is 7 days or 5 GB per Prometheus instance. Alloy has a persistent remote-write WAL with finite retention; endpoint-outage behavior is bounded and needs runtime testing.
- Alertmanager runs as a CM peer pair. Prometheus retains a per-replica external label on stored metrics but drops it from outgoing alerts so identical alerts can be deduplicated. Duplicate suppression and the recovery dispatcher's behavior still require acceptance testing.
- Alloy tails configured local system/auth/cloud-init/Nginx/Ansible logs and writes each log once to the local loopback Loki proxy. The proxy uses Nginx round-robin and passive failover across CM Loki services addressed by inventory Tailscale DNS FQDN, with TLS certificate verification enabled.
- Loki on each CM uses Azure Blob as shared object storage, memberlist over Tailscale for its ring, and replication factor 1. WAL and TSDB shipper index/cache remain local; chunks/index are stored in Blob. Chunk idle/max-age settings are 30 minutes/1 hour to batch Blob writes. The Storage Account is ZRS and CMK-encrypted. No Azure Load Balancer is used for telemetry.
- The desired tailnet domain is `fairy-kanyu.ts.net`; source config uses the FQDN discovered by `ansible/inventory/generate_inventory.sh`. The current design target is 2–3 CM nodes, with a design ceiling of 5 subject to quota/cost checks, and up to 250 workload nodes. Scale-out is not autoscaling or runtime-accepted; validate region quotas and resource headroom first.
- The recovery dispatcher is a separate Prometheus-alert consumer, not a Loki-log processor. It maps a bounded alert allowlist to fixed remediation wrappers. It uses the `recovery-state` blob and a lease for shared cooldown/idempotency coordination between CM nodes, and writes a local audit log. Removing the Storage Account also requires an explicit replacement/retirement decision for this shared coordination.
- Workload managed identity retrieves the Cloudflare API secret from Key Vault at runtime, obtains a Tunnel Token, and starts/refreshes `cloudflared`. GitHub Actions does not perform that runtime secret retrieval. GitHub-hosted Terraform jobs do currently need Key Vault key access for the separate CMK configuration noted above.
- PostgreSQL HA implementation is now represented in source: Terraform defaults to three workload DB members across zones, supports optional per-node data disks, creates a dedicated backup identity/container in the existing Blob account, and scopes ports/RBAC. Ansible configures PostgreSQL 16 with Patroni, three-member etcd, local HAProxy, runtime Key Vault credential retrieval, a transactional/idempotent demo app, daily base backup plus WAL archive helpers, and basic HA/backup metrics and alerts. RPO/RTO are **targets only**: synchronous failover RPO 0 for acknowledged transactions on a single member loss (conditional), failover RTO 300 seconds, WAL archive/PITR RPO 300 seconds, and restore RTO 7200 seconds. PITR retention target is 7 days, with a 9-day Blob lifecycle cushion. No Azure apply/deploy, real Blob transfer, failover/partition test, database restore drill, capacity test, or watchdog acceptance has been performed. Softdog availability/fencing and coordinated TLS certificate rotation remain runtime risks. The full validation script reaches its final repository-wide diff check but is blocked by whitespace in the workspace's broader pre-existing changes; focused Terraform/Ansible/Python validations are recorded in the implementation decision file. Application rollout rollback must never restore DB state or discard writes.
- Cloudflare tunnel gateway selection is represented as a per-VM `cloudflare_ingress` Terraform field/tag. Inventory generation creates a `cloudflare_ingress` group; the Cloudflare role is limited to that group and validates one configured tunnel with a 2–25 connector cap. Other workload VMs remain app/Nginx backends. The current default selects both existing workloads. There is no Cloudflare API automation for tunnel creation or hostname/DNS routes.
- Workload Nginx builds its backend pool from all online workload inventory hosts, with TLS verification, passive failure handling, bounded retries, and `/livez` plus upstream-backed `/readyz`. A 15-second systemd watchdog checks gateway readiness and stops/re-enables `cloudflared` after configured consecutive failure/recovery checks. This is best-effort failover and has not been runtime-tested; Cloudflare connector selection/retry timing is not guaranteed to prevent all failed requests. CPU/RAM-aware balancing is not implemented.
- GitHub Ansible deploy packages the triggering reviewed commit (or an operator-selected full SHA through protected manual dispatch) as an immutable SHA-marked archive and transfers/stages it on every online ready CM over authenticated Tailscale SSH; CM no longer fetches from GitHub or requires repository visibility/credentials. After successful deployment, CI synchronizes the last-good release pointer across ready CMs. Cloud-init prepares release storage and a stable controller symlink instead of cloning a public URL. `deploy-approved-release.sh` runs a canary then percentage batches with resource/health gates, logs to `/var/log/ansible/site.log`, and attempts rollback on failure. These changes are code-present but not acceptance-tested; first deployment has no previous release to roll back to.

### CI, policy, checks

- `.github/workflows/` contains Terraform identity/VM plan, protected apply/destroy, Ansible checks/deploy, and Tailscale policy workflows. Terraform uses GitHub OIDC; Ansible deploy joins Tailscale and triggers execution on an available CM over SSH.
- `tailscale/policy.hujson` is the Tailscale access policy source.
- `ansible/scripts/validate-repo.sh`, `ansible/scripts/smoke-test.sh`, and `ansible/tests/` are the repository's static/unit/smoke validation entrypoints. Passing static checks does not prove Azure deployment, failover, or runtime acceptance.

## Agreed observability architecture

1. Keep CM/workload HA pools and observability on existing VMs; no extra VM or Azure Load Balancer for telemetry. Target 2–3 CM nodes initially, with a design ceiling of 5 subject to quota/cost checks, and up to 250 workloads. This is provisioning capacity, not autoscaling or runtime acceptance.
2. Use Alloy as the sole host agent. Keep selected Unix exporter metrics and the 15-second interval, filter series at source, and push to every CM Prometheus over verified Tailscale TLS. Each Prometheus retains data locally; Alertmanager receives replica-deduplicated alerts. PostgreSQL remains basic readiness/availability; temperature/GPU are collected only if exposed by the VM.
3. Use stateless, shared-Blob-backed Loki with memberlist over the tailnet, replication factor 1, and one Alloy log write through the local Nginx proxy. The proxy provides passive failover over Tailscale TLS. This supersedes the earlier local-filesystem Loki/log-dual-write proposal. Keep source logs selective and the 30m/1h chunk timing to limit transaction volume. Runtime Blob access, proxy failover and alert dedup still need testing.
4. The intended tailnet is `fairy-kanyu.ts.net`; source config uses FQDNs discovered by the inventory generator. No paid Azure Load Balancer or extra monitoring VM is added. Existing Blob ZRS, CMK, Key Vault and remote Terraform state have normal charges.
5. Keep Key Vault for workload runtime Cloudflare-secret retrieval. Any Key Vault service-endpoint/firewall conversion is a separate networking decision and is not included in this observability refactor.

## Current phase/status

Core Terraform, Ansible roles, CI workflows, Alloy-based observability, release deployment orchestration, and bounded recovery code are present. The shared-Blob Loki, Alloy push/fan-out, Tailscale TLS, canary/rollback, and connector-watchdog configurations are represented in source, but deployment, scale, and failure behavior are **not accepted until relevant validation and runtime failure tests have actually run**. External human notification channels are not configured. Update this file whenever implementation status or source locations change; record architecture decisions and unresolved tradeoffs in `IMPLEMENTATION-DECISIONS.md`.

Remaining work includes PostgreSQL Azure Blob integration and restore drills, forced failover/network-partition testing, watchdog and TLS-rotation acceptance, representative capacity tests, end-to-end rollout/rollback acceptance, Cloudflare connector failover verification, notification-channel approval/configuration, and tunnel/hostname automation decisions. See `IMPLEMENTATION-DECISIONS.md` for feature requirements and open choices.
